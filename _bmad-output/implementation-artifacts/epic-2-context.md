# Epic 2 Context: Take only what you need

<!-- Generated from planning artifacts. Regenerate with compile-epic-context if planning docs change. -->

## Goal

Today the stack is a single monolithic `compose.yaml` with two profiles, so the granularity of choice is one of four whole-profile combinations — a developer who wants only Postgres and Redis still boots Keycloak and, if observability is on, a gigabyte of it. This epic decomposes that monolith into per-service Modules, each a self-contained directory owning its Compose fragment, config, seed data, verification check and documented failure modes, reassembled through Compose `include` on top of a shared base fragment. On top of that it adds Selection — asking for a set of Services and getting exactly that set, with cross-Module dependencies expanded automatically — named Bundles for the sets used together, a per-Module completeness contract that CI enforces in both directions, and a smoke suite whose checks follow the Selection. It carries the epic's one visible behaviour change: giving every Service a profile means a bare `docker compose up` with no profiles set goes from starting the core five to starting nothing at exit 0, so the migration path for existing `.env` files is part of the work, not an afterthought. Structurally the epic depends on nothing, but it is deliberately sequenced after the verification epic so the refactor has a safety net, and after the image-bump wave so a major upgrade and a file split are never being debugged at the same time.

## Stories

- Story 2.1: The shared fragment and the first Module
- Story 2.2: The remaining core Modules
- Story 2.3: The admin and observability Modules
- Story 2.4: Every Module carries its own contract, enforced
- Story 2.5: Selecting a Module brings what it needs
- Story 2.6: Bundles, and a safe path through the breaking change

## Requirements & Constraints

- **Data durability is the hard gate.** Named volumes are the only irreplaceable thing in the repository; a renamed or re-driven volume orphans real data silently, with no error. Volume identifiers are frozen permanently and never tidied to match a renamed Module — object storage keeps `minio-data`. Capture a volume inventory before each extraction and diff it after; a non-empty diff stops the work. `down` then `up` must preserve every stateful Service's data, and only an explicit confirmed destroy may remove volumes.
- **The rendered-config diff is the primary verification** for every extraction. Capture `docker compose config` before the change and compare after: the two must be identical apart from key ordering. This is the highest-value check in the migration and outranks any narrower assertion.
- **Exactly what was asked for starts, and nothing else.** Selecting `postgres, redis` yields two containers and creates no other Service or volume. Selecting a Service with dependencies expands to include them.
- **An incoherent Selection fails before anything starts**, naming the missing Service, and creates no container or volume.
- **Nothing may silently skip or silently no-op.** An empty resolved Selection is an error, not a quiet exit 0. A smoke check whose Service or fixture is unavailable fails rather than reporting success. A contract check runs against every Module and every Bundle.
- **A Module is complete or it is rejected**: healthcheck, smoke check, endpoint metadata, a seed declaration (data or an explicit justified no-seed marker), and a gotchas file. Presence-based only — never a judgement about whether seed data was warranted.
- **Smoke checks exercise real function** — mint a token, round-trip an object, publish and consume — never liveness. Carving the central script into per-Module checks must leave the suite's pass count unchanged.
- **Isolation and startup budget hold throughout**: published ports bind to the configured bind address (loopback by default), and a full Selection reaches all-healthy in under two minutes on a warm cache with the start path blocking until healthy.
- **Every Bundle states its approximate memory footprint** so choosing one is informed.
- **The security posture is fixed, not improved.** Reject any change that partially hardens the stack, including one arriving incidentally inside a refactor.

## Technical Decisions

- **Microkernel split.** A Core Substrate — the include registry, the shared fragment, the network, the configuration namespace, volume identity, the host-port table, the Bundle registry, the resolver and the task surface — plus pluggable Service Modules under `services/<name>/`. Dependencies point inward only: Core never depends on a Module, and a Module never edits another Module's file. A Module touches Core solely to add its own registry entry, its identifier-only volume declaration, its port-table row and its Bundle membership.
- **Shared configuration flows through `extends` against a file reference, never YAML anchors** — anchors are document-scoped and cannot cross `include`. The shared fragment declares only `restart`, `logging` and `networks`, never `depends_on`, `links`, `volumes_from` or `network_mode: service:*`, because `extends` inherits those keys without importing the resources they name. It is referenced by `extends` only and never appears in the include list. Any one-shot helper extending it must override `restart: "no"` or it restart-loops.
- **A Module's top-level `volumes:` and `networks:` stanzas carry the identifier and nothing else** — no driver, no `driver_opts`, no `attachable`. Keys the root omits are last-include-wins, so a Module adding a driver key silently wins and include ordering could change a volume's driver.
- **Cross-Module dependencies are `depends_on` with an explicit condition, and that is the validation gate.** `docker compose config -q` is the mechanism; no bespoke dependency resolver is written. A dependency not expressed that way is unenforceable and therefore does not exist. Known blind spot: `config -q` cannot see host-port collisions, so rendered config is parsed for duplicate published ports separately.
- **Selection is resolved to its transitive closure before Compose sees it**, by a Core resolver script that emits the profiles value; every task invoking Compose goes through it. A Module carries a profile equal to its own name plus its Bundle profiles; a service starts when any of its profiles is active. Bundle names live in a Core-owned registry while membership is declared per service — a `profiles:` key on an `include` entry is silently ignored. Every registered Bundle must already be dependency-closed, asserted by CI, so no Bundle relies on runtime expansion.
- **Module validity is closure validity.** A Module validates together with its transitive dependency closure, computed by the resolver and never hand-maintained. Standalone validation is vacuous: with a profile on every service, validating one Module file alone renders no services and exits 0. Paths are always relative to the Module's own directory; no absolute paths, and `project_directory` is never used.
- **One primary Service per Module plus explicitly declared helpers** named `<module>-<role>`, each carrying a profile set identical to its primary's — a helper with different profiles produces an unseeded Service that starts fine and fails its smoke check. The contract check runs both directions: every Module directory maps to a Service and every rendered Service maps to a Module.
- **A Module declares what it needs from another Module in its own file** as an `x-requires:` block, reconciled by CI against the provider's configuration. Endpoint metadata lives per Module as an `x-endpoints:` block and is the sole input to generated connection documentation later.
- **Configuration namespace is flat, global and two-tiered**: Module variables named `<MODULE>_<CONCERN>` in the root env file, and contract variables whose names are externally dictated, each registered to exactly one owning Module. Per-Module env files are forbidden — a child env file can only ever be a fallback, never an override.
- **Ports come from one Core-owned allocation table**, published as bind-address-first with a Module-variable default; a new Module takes the next free range rather than picking ad hoc.
- **Core scripts are verified like code**, not trusted like config: shellcheck-clean, `set -euo pipefail`, with tests. The resolver in particular is tested for closure correctness, refusal of an empty Selection, and refusal of an unknown Module or Bundle name; those tests run in CI and may not be skipped.
- **Extraction order is prescribed**: the shared fragment plus Postgres first because it has no dependencies, isolating the mechanism from the closure problem; then the rest of the core batch; then admin; then observability; then the resolver, Bundles and the breaking change. Each batch is its own reviewable change with its own config diff and volume inventory. Rollback for an extraction is reverting the commit — no volume is touched.
- **Migration mitigations for the breaking change are all three**, not a choice among them: the shipped example env file ships a non-empty default Selection, the resolver fails loudly on an empty resolved Selection with a message naming the variable and the fix, and the change leads the README and release notes.

## Cross-Story Dependencies

Strictly ordered. Story 2.1 proves the decomposition mechanism on the simplest case — the shared fragment plus a dependency-free Service — and every later extraction repeats that pattern; get it wrong here and it is wrong thirteen times. Stories 2.2 and 2.3 extend it to the remaining Modules, 2.2 first because cross-file `depends_on` and the declared-helper pattern surface there, 2.3 last because the collector fan-out and the telemetry round-trip are the most entangled. Story 2.4's contract and CI checks depend on every Module existing, since the check runs in both directions and fails on any Service without a Module. Story 2.5's resolver depends on the full Module set and its `depends_on` graph; 2.4's smoke carve-out feeds the runner that 2.5's resolved Selection drives. Story 2.6's Bundles depend on the resolver, because dependency-closure of each registered Bundle is what CI asserts, and it is where the breaking change and its migration path land.

Upstream: structurally independent of the verification epic, but sequenced after it — CI and the image-bump wave are the safety net, and debugging an upgrade and a refactor together is the worst available ordering. Downstream: connection documentation is generated from each Module's endpoint metadata, backup scope follows the Selection, gotchas become per-Module files, and every new Service in the catalog epic enters through the Module contract established here.
