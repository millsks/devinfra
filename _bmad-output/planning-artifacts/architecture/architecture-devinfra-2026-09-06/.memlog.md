- (decision) PARADIGM: microkernel (plug-in) architecture. A minimal core substrate — the include registry, one shared base fragment consumed via extends, the devinfra network, the root .env namespace, and the task runner — plus interchangeable Service Modules that plug into it. Chosen because the shared-substrate/leaf-plugin split is exactly what the verified Compose mechanics force: network, env and volume identity cannot be module-private, while service definitions can.
- (decision) AD: Modules are self-contained directories. services/<name>/ owns compose.yaml, conf/, seed/, smoke.sh and gotchas.md. Config assets move out of the shared docker/<name>/ tree into the module. Prevents: a module that cannot be lifted into another repo, which would foreclose PRD Q1 option A.2.
- (decision) AD: every Module file must be standalone-valid — 'docker compose -f services/<n>/compose.yaml config' exits 0. This is the concrete mechanism that keeps the reusable-base consumption model reachable without committing to it.
- (decision) AD: volume names are FROZEN. Renaming a named volume orphans its data and violates NFR-1, the most load-bearing property in the PRD. A module rename must never rename its volume.
- (decision) AD: Bundles are named profile sets, not files. Every module service declares profiles: [<module>, <bundle>...]; a service activates if ANY of its profiles is active. Selection = the COMPOSE_PROFILES value. Forced by the verified inability to attach profiles at include level.
- (decision) AD: giving every service a profile is a BREAKING change to bare 'docker compose up' (services with no profile always start; services with profiles do not). Mitigation: .env ships a default COMPOSE_PROFILES covering the core bundle. Must be called out in the migration plan.
